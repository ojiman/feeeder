# Feeeder アーキテクチャとエージェント実行ハーネス

更新日: 2026-10-05

## 1. 位置づけ

製品要件は[PRD](specification.md)を正とする。本書はV1の技術設計と、AIエージェントに実装を任せる際の実行ハーネスを定める。記載したハーネスは合格証拠が揃うまで有効とみなさない。各試験結果は`PASS / FAIL / NOT_RUN / BLOCKED`で記録し、入力hashと実行環境に結び付ける。

第2〜5節は実装済みV1の設計・検証経緯を記録する。Dogfoodingに基づく変更案は第6節で差分として扱い、PRD改訂全体のPdM承認後に適用する。変更案は未実装・未検証で、過去のPASSを流用しない。

## 2. V1の技術構成

- macOS 26.6以降のネイティブアプリとしてSwiftUIを使い、ローカル永続化はSwiftDataを基本とする。フィードと原文は端末からURLSessionで取得し、RSS/AtomはXMLParserで解析する。原文のアプリ内閲覧にWebKitを用いる。Backend、アカウント、AI proxyは置かない。
- V1は専用保存先`Application Support/Feeeder/Reader.store`の空DBから開始する。プロトタイプのデータ移行・互換モデル・日時補完は実装対象外。通常起動でデモを挿入せず、デモは明示指定時に限る。V1で保存したデータは再起動と以後のモデル追加で保持する。
- 購読元、フィード内での所属、記事の同一性、原文URL、RSS要約、取得本文とそのカバー範囲、最初の既読日時、週ノートと出典の関係を区別して保存する。再受信で既読日時やノートを上書きしない。既読日時は記事内容が右ペインへ初めて表示された時刻とし、再表示では更新しない。
- 既読日時はタイムゾーンに依存しない時点として保存する。その週の初回ノート作成時にMacの現在のタイムゾーンで月曜始まりの週の範囲を決め、開始時点・終了時点（終了を含まない）・タイムゾーン識別子・表示用の暦日範囲を週に保存する。現在週の下書きも作成時に固定し、同じ週の追加ノートは保存した範囲を共有する。作成済みの週の候補記事は保存した範囲で集計し、期間表示も保存した暦日範囲とタイムゾーンを用いる。Macのタイムゾーン変更で保存済みの範囲・既読日時・ノートの本文・採用済み出典を書き換えない。V1には表示言語・タイムゾーンを変更するアプリ内設定を追加しない。
- 本文抽出はベストエフォートとし、抽出に失敗した場合は保存済みRSS要約を表示する。表示できた範囲を本文全体と誤認させない。原文へは常に戻れる。ログイン・購読制限を回避する取得は行わない。
- 入力URLはschemeとredirect先を検証し、XML外部entityを拒否し、抽出HTMLを安全な読書表示へ変換する。原文閲覧は抽出本文と分離する。記事本文とツール出力は未信頼データとして扱う。
- 保持期間内の記事本文・RSS要約と保存済み週ノートはオフラインで読める。記事本文・RSS要約の保持期間は初期値30日とし、Settingsで変更可能にする。期限の起算点は未読記事では初回受信時、既読記事では初回既読時とし、再受信・再表示で更新しない。記事の同一性・既読日時など再受信の重複排除と週の候補集計に必要なメタデータを、期限付きの本文・RSS要約と分離する。ノートの出典タイトル・URLは本文削除や購読解除に依存しない形で保持する。ノート採用によって元記事全文を無期限に複製しない。期限切れ本文・RSS要約の削除はノートや出典に連鎖させず、ノートの自動削除は行わない。保持期間短縮・手動削除はPRDで定めた対象表示と確認を伴う。削除済み本文は閲覧・AIパッケージのレビューで利用できないことを示す。
- ソース公開の対象はコード・仕様・合成サンプル／テストデータとし、本人の購読情報・閲覧履歴・取得記事・ノート・認証情報をリポジトリに含めない。公開前に対象の差分と履歴を確認する。製品受入後の公開判断と具体的な外部書込みは別に扱い、今回の方針確定だけで公開操作を行わない。Apache-2.0のLICENSEを同梱し、第三者コードを追加する際は各ライセンス・著作権表示・必要なNOTICEを保持する。Apache-2.0はプロジェクトコードに適用し、第三者の記事、feed、商標、サービス規約には適用しない。

## 3. AIハンドオフ

V1の連携先はClaude Desktopのみとする。週ノートまたは単一記事から、選択した出典、実際に使うテキスト、本文のカバー範囲、出力言語、依頼文を含む確認可能なパッケージを作る。利用者は出典を個別に除外できる。利用者によるパッケージ確認と「Claudeで開く」の操作後に、生成ファイルと依頼文をClaude Desktopの送信前の入力欄へ渡す。Claude側の送信と返答の採用は本人の操作に限り、アプリは自動送信・自動書込みをしない。出典は実際にパッケージに含めた内容だけを指す。

[Claudeの公式案内](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link)にあるCowork起動リンクを、現時点のV1実装経路とする。製品体験としては利用者が希望する通常Chatを第一希望とするが、公式のChat起動リンクで記載されているのは依頼文の事前入力までで、Chatへの自動ファイル添付は未検証。「Chatでは実現不可能」と結論づけたわけではなく、今回は経路調査を広げず検証済みのCoworkを実装案とする。`claude://cowork/new`の`q`に短い依頼文、`file`に生成パッケージの絶対パスをURLエンコードして指定する。本文・RSS要約・出典・カバー範囲・出力言語・完全な依頼文はUTF-8のTXTファイルへ保存し、ファイルの内容を確認可能にする。`q`は約14,000文字で切り詰められるため、記事内容を起動リンクに詰め込まない。通常チャット用の起動リンクに未文書化のファイル添付パラメータがあるとは仮定しない。

この経路のファイル添付・依頼文の事前入力・送信前の停止を、対応するClaude Desktopの版とアカウント環境で合成パッケージを使って実機確認する。Claude Desktopが起動済み／未起動の場合、日本語と空白を含むファイルパス、長い記事本文を含む場合でも選択ソースが保持されること、利用不可や起動失敗時の再試行を確認する。公式文書の存在だけではPRD-05を合格にしない。コピーとファイル書き出しは失敗時の復帰手段であり、通常の直接起動・添付体験の代わりにはしない。添付上限を超える場合は内容を保持した分割などの別経路をレビュー可能にする。アプリが生成する一時パッケージを、元記事本文の無期限保存経路にしない。

[2026-10-04〜05の実機検証](verification/2026-10-04-claude-desktop-handoff.md)では、Claude Desktop 2.19675.0のPro環境で、起動済み／未起動からの遷移、依頼文の事前入力、Attach許可後の添付カード、送信前停止を確認した。利用者による送信後、約26,000文字の合成TXT全体のSHA-256と日本語・2出典の情報も元ファイルと一致した。添付キャンセル後の再試行も成立した。Claude側ではAttachの許可と、送信後の親フォルダへのアクセス許可が別に必要で、同じフォルダでも新しいセッションで再度許可が出た。リンク由来の依頼文には注意表示が出た。親フォルダへの許可は読取り・変更を可能にし、クラウドで使うファイルは端末を離れる旨を表示したため、選択したソースの生成パッケージだけを置いた専用の一時ディレクトリを使い、元の保存データから独立したコピーを渡す。添付プレビューは読込エラーとなったが、本文の読取りは成立した。この環境で連携経路の技術検証は完了・PASSとするが、Feeeder本体の実装・異常時の復帰UI・他環境は未検証でありPRD-05全体の合格にはしない。

不在ファイルでもClaudeはAttach確認と添付カードを表示した。起動前に生成ファイルの存在・通常ファイルであること・読取り・確認済み内容との一致をFeeeder側で確認し、起動成功やカード表示だけを受け渡し成功の証拠にしない。Claudeでの送信・読取りが起動後に行われるため、起動成功を理由に一時ファイルを直ちに削除しない。具体的な保持期限・削除タイミングは実装設計で決める。

## 4. AIエージェントに実装を任せるためのハーネス（V1）

V1は利用者が会話と差分を確認できる対話型開発を基本とし、実装者は同時に1名とする。専用の無人worker、常駐broker、VM群、役割別の権限サーバーは作らない。以前の試験結果は現在のCodex設定の合格証拠ではない。実行時の境界はCodexとOSの設定で決まり、AGENTS.mdの指示文だけでは強制できない。厳密な秘密の読取隔離を証明できていない環境で無人workerを起動しない。

### 4.1 できること（パーミッション）

- 追加確認なし: 割り当てたリポジトリ内の編集、合成fixtureを使うビルドとテスト、差分確認、作業で生成した一時ファイルの削除、ローカルcommit。失敗したテストの修正・再実行も含む。
- パターンで禁止: sudoやsandbox解除、認証情報の読取、破壊的なGit reset/clean、任意の外部scriptの取得・実行、mainへの直接push、許可されていない公開・配布。コマンド名の列挙だけを防御境界とはみなさない。
- 中身を確認する: 外部依存の追加、実サイトのフィード／本文fixture取得、既存利用データの移行・削除、GitHubへのbranch push・PR、署名・配布。対象URL、変更差分、データ範囲、宛先を確認する。利用者がその操作を今回の依頼で既に指示していれば、同じ許可を取り直さない。

### 4.2 届く範囲（実行境界）

作業対象はこのリポジトリと、破棄可能な非秘密のビルド・テスト用 /private/tmp 領域に限る。Xcode SDKなど必要な開発ツールは読取のみとする。本人の読書DB、Documents、Downloads、ブラウザprofile、SSH鍵、他repoを入力にも作業領域にも含めない。通常のテストは合成fixtureで完結させ、shellからのネットワーク取得は対象を確認した作業に限る。/private/tmp は共有領域であり、ロール間の隔離には使わない。

対話型作業ではプラットフォームのsandboxと承認UIを使い、専用containerを追加しない。現在の環境で個人ファイルの読取やKeychain IPCをOSレベルで完全に拒否できるとは主張しない。この制約を受け入れられない作業、または無人実行は、専用macOSアカウント等の隔離環境と否定試験を用意してから別途判断する。

### 4.3 鍵の渡し方（クレデンシャル）

| 対象 | V1での経路 | エージェントへの入力 |
|---|---|---|
| ローカルDB | 合成の一時DB | 本人の読書履歴・本文・ノートを渡さない |
| 公開RSS／記事 | 確認済みURLから取得したfixture | Cookie、Authorization、個人識別queryを除く |
| Claude Desktop | アプリ利用者が確認したパッケージを直接起動・添付の経路へ渡し、Claude側で送信する | APIキーを使わない |
| GitHub | 利用者が依頼した範囲をホストの認証済みツールで実行 | token・SSH鍵を直読み、コピー、環境変数で受け渡ししない |
| Apple署名・App Store | V1の受入対象外 | Apple ID、証明書、秘密鍵を渡さない |

秘密を使わないことで済む経路を選ぶ。本人の通常accountでKeychainの自動probeを実行しない。将来BYOKや無人workerを採用する場合は、鍵の保管・代理実行・隔離試験をその機能の設計時に定める。

### 4.4 サブエージェント構成（オーケストレーション）

V1の通常作業は実装者1名とし、サブエージェントを常用しない。変更後はテストと差分を確認し、保存モデルの移行や公開に関わる変更では、必要に応じて同じcommitを対象に読取専用のTechLeadレビューを依頼する。PdMはPRDの利用シナリオを実機で確認して製品を受け入れる。レビュー者が同じ作業コピーを書ける状態なら「独立した読取専用検証」とは呼ばない。子エージェントへ全会話、本人データ、認証情報を渡さない。

### 4.5 ハーネスの受け入れ条件

以下は製品機能とは別に判定する。通常の対話型開発では、各変更の対象commit、実行したコマンドと終了コード、差分、利用したfixtureを記録する。必要な記録がない項目はNOT_RUNとし、指示文を境界試験のPASSに代えない。

| ID | 軸 | 合格条件 |
|---|---|---|
| H-P01 | パーミッション | git diff --check の終了コード0。差分pathは宣言した対象内。外部変更の操作ログは今回の依頼で指定した宛先・操作に一致し、mainへの直接pushは0件 |
| H-B01 | 実行境界 | 実効profileの書込rootとネットワーク設定を記録し、生成物pathは作業コピーか専用一時領域内。包括的なsandbox解除と無人worker起動は各0件。実効profileを読み戻せなければNOT_RUN |
| H-C01 | クレデンシャル | テスト入力一覧は合成または確認済み公開fixtureのみ。実行ログ上、credentialの直読み・引数／環境変数での受渡し・Keychain probeは各0件。これは秘密領域へのOSレベルの到達不能を証明する条件ではない |
| H-O01 | オーケストレーション | 同時writer数1以下。テスト結果に対象commitまたは作業treeのhashを記録し、レビュー対象と一致。source変更後の古い結果を採用0件。テスト終了コード0、または未実行理由を記録 |

無人workerを将来使う場合は、この軽量な対話型ハーネスを流用して隔離済みと主張しない。別プロセスのファイル・通信・Keychain境界を否定試験で確認し、権限を広げずに動くことを採用条件とする。V1の機能実装やPdMレビューを、その将来用の基盤づくりで止めない。

## 5. 実装結果と残る技術検証（2026-10-05）

- 本文抽出はSwiftSoup 2.13.9で`article`、次に`main`内の段落をプレーンテキストにする。日本語charset・段落・制限ページ・robotsは合成fixtureで確認済み。抽出は全文保証ではなく、取得できない場合はRSS要約へ戻る。本文抽出のHTTP redirectは追わず、未検査の転送先へ取得を進めない。実サイトでの品質は未検証。
- 本文・RSS要約の保持設定は7 / 30 / 90 / 365日、初期30日。記事の同一性・初回受信／既読と本文snapshotを分離し、ノート出典はタイトル・URLを独立保存する。本文読取・AIレビュー・起動前で期限を検査し、起動／復帰・稼働中30分ごとに物理削除する。期限削除による復活禁止とV1保存データの再openは合成DBで確認済み。
- AIパッケージは不変の全文・出典・Coverage・言語とSHA-256を持つ。操作UUIDごとの専用フォルダに0700、TXT・管理metadataに0600でコピーする。期限は生成から24時間と含む本文の最早期限の小さい方。保持短縮・削除・次のコピー期限・起動／復帰で同期し、本人の書き出し先は変更しない。分割は1MiB/part以下でUTF-8と元の全byteを保持する。これはClaudeの公称上限ではない。
- Claude Desktop 2.19675.0 / Pro / Coworkで、Feeeder本体から起動済みアプリへの遷移、Attach取消後の再試行、本人によるAttach後のカード、送信前停止を確認した。未起動からの本体連携でも本人によるAttach後のカードと送信前停止を確認済み。1,391,085 bytesの本体レビュー・TXT／分割書き出し・起動前bytes照合・Attach確認まで成立した。大容量のClaude側読取り、他版・他プランは検証を残す。以前の技術probeのPASSと、本体の製品受入を区別する。
- 読書一覧は計測を受けNSTableViewで表示し、SwiftDataモデルのIDを毎回全件読まないよう索引を持つ。利用者承認を受け本文scrollもNSTextViewへ移し、ビューを再利用してlayerで短い遷移を行う。100回切替×3で更新開始p95は78.06 / 80.62 / 76.72msとなった。高速入力で中間表示は統合されるため標本数を併記する。原文10往復の選択・列幅・focus復帰を確認。MainActor停止の原因判定と原文復帰の絶対位置精度は継続中。性能・IME・VoiceOver・Reduce Motion・参考動画との操作感比較は、[実機受入記録](verification/2026-10-05-v1-acceptance.md)で未完了を明示する。2026-10-05に本人がmain統合を承認し、残る確認と最終PdM判断をDogfoodingへ移した。

## 6. Dogfooding改訂の設計案（PdMレビュー待ち・未実装）

### 6.1 保存モデルと実際のV1データの保持

`Article`に任意の`starredAt`を追加し、非nilを現在のStar状態とする。最初の付与と解除後の再付与で現在時刻を保存し、解除ではnilにする。`firstReadAt`・`firstReceivedAt`・保持期限は変更しない。再受信・本文期限削除でもStarを上書きしない。関心の全操作履歴を記録するイベント基盤は作らない。

日次ノートは既存の`WeeklyPeriod`／`WeeklyNote`を日次へ変換せず、`DailyNote`と`NoteScrap`を追加して保存する。`DailyNote`はID、固定した日の開始・終了（終了を含まない）・タイムゾーン・表示用暦日、タイトル、編集本文、作成日時、更新日時を持つ。現在時刻を含む保存済みノートを優先し、該当がなければMacの現在の暦日で作成する。時計変更等で複数が該当する場合は作成日時が最も新しいものを使い、既存ノートを移動・結合しない。日付キーだけで異なるタイムゾーンの期間を上書きしない。

`NoteScrap`はノートIDと記事IDで重複を防ぎ、タイトル、URL、保存済みRSS要約、RSS由来のカバー範囲、保存日時、本人のメモを独立保存する。RSS要約は保存時点で利用可能なものを読書表示と同じ方法でテキスト化し、全文抽出で置換しない。要約なしは欠如として扱い、タイトル・URLのみであることをカバー範囲に示す。二度目の保存は既存スクラップを返し、保存日時・内容・メモを上書きしない。保存に失敗した場合は新規の日次ノートとスクラップを部分的に確定せず、UIで失敗を示して再試行可能にする。

週ノートの`NoteSource`には任意の保存済み要約・カバー範囲・スクラップ日時を追加する。日次スクラップからの採用時にコピーし、元のノート・記事への連鎖削除を行わない。既存出典の新しい項目はnilとし、過去の要約・付与日時を推測で補わない。既存週ノートの本文・出典は自動変換しない。

これは**配布済みV1のデータを保持する追加モデル変更**であり、対象外のプロトタイプ移行とは別である。ストアを削除して作り直さず、変更前スキーマの合成ファイルDBを新スキーマで開き、購読・記事同一性・既読日時・本文期限・週期間・ノート・出典の保持を確認する。SwiftDataによる追加変更で保持できるかを実装時に検証し、失敗時に実データを消して復帰する処理は入れない。検証した方式と対象スキーマを実装計画・受入記録へ明記する。

### 6.2 候補集計と保持・AI入力

週の初期候補は保存済み週期間に入る現在の`starredAt`と日次スクラップの保存日時から集計し、記事IDで重複排除し、同じ週の複数スクラップは最初の保存を初期選択にして、本人が別の保存内容も選べるようにする。別途`firstReadAt`による既読履歴を選べるようにする。候補は操作で変わり得るが、固定済みの週期間と採用済みノートを再計算・変更しない。利用可能な週の一覧には既読日時に加えStar付与・スクラップ保存日時と保存済み週を含め、既読履歴がなくても関心の記録を見つけられるようにする。

元記事の本文・RSS要約は従来の期限で削除する。明示保存したスクラップ要約と週ノートへコピーした要約はノートの所有データとし、自動削除の対象にしない。元記事全文は複製しない。画像はノート所有の永久データにはしない。

AIレビューは日次・週ノートの保存済み出典も扱い、保存済み要約と現在保持している記事内容を区別して選択する。同じ記事の両方を無言で重複入力せず、実際に選択した内容・カバー範囲・保存日時をパッケージへ記録する。保存済み要約はRSS由来であり、記事全文やAI生成要約とは表示しない。期限切れの元記事内容を補完・復活させない。記事由来の内容を含む一時パッケージは従来どおり最早の本文期限と生成24時間を上限とし、ノート所有の要約だけの場合は生成24時間を上限にする。起動前の内容一致検査・専用ディレクトリ・手動送信・再試行の契約は維持する。本人の書き出し先は自動削除しない。

### 6.3 共通3カラムとキーボード

既存の`NavigationSplitView`を共通の枠として使い、現在のNotes専用画面への全体切替を、中央のノート一覧・右の編集へ変更する。左にFeeds／Notesを残し、購読追加・更新は左上、選択記事のAI・Star・スクラップ・原文操作は右上に配置する。FeedsとNotesの選択・スクロール記憶を分け、往復で復元する。Star解除で選択中の記事が対象外になっても次の移動まで選択と位置を維持する。記事リストのNSTableViewと読書本文のNSTextViewは維持し、今回の整理だけで表示基盤を入れ替えない。

アプリ内原文のWKWebViewと記事一覧から、同じ`j/k/s/n`操作を実行する。日本語変換中、入力欄、修飾キー付き標準操作には割り込まない。原文表示中に記事を移動した場合は新しい選択記事の原文URLを使い、古い本文描画・取得完了が新しい選択や既読状態を変えないようにする。有効なURLがなければ選択記事の読書表示へ戻る。`Esc`は現在の記事の記憶した読書位置へ戻す。Star・スクラップ操作は原文のスクロールとフォーカスを維持し、成功／失敗を読み取れる表示で伝える。

### 6.4 フォルダと画像

フォルダは既存の`Feed.folder`を使う1階層を維持し、所属購読の割当・移動・名前変更と、フォルダ選択時の所属feed集合による記事集約を追加する。新しいフォルダの指定は購読の割当と同時に行い、空フォルダを保持するモデルや入れ子の木構造は追加しない。記事の集約・未読件数は`FeedMembership`の所属を使い、複数購読に属する同じ記事を重複計上しない。

Faviconは購読元のアイコンとして、サムネイルは記事の画像として扱う。RSS/Atomの画像enclosure・media情報・本文内の画像から利用可能なURLを選び、記事画像のない一覧行には空き枠を強制せず、画像が後着してもレイアウトを変えない領域を確保する。購読元サイトのアイコン取得はベストエフォートとし、第三者のFavicon APIへ購読URLを送らない。RSS/HTMLに書かれた画像URLも未信頼として既存のscheme・redirect検査を適用し、画像のサイズ・取得量に上限を設ける。

画像取得・縮小をMainActorで行わず、表示対象を優先し、URLSession／ローカルの容量制限付きキャッシュを使う。上限値と消去条件は実装計画で具体化する。キャンセル・失敗・オフラインではテキストをそのまま読める。画像の到着で行高・選択・スクロール位置が変わらないことを確認し、既存の連続入力性能計測と原文復帰確認を再実行する。

### 6.5 範囲と検証

次回ベータへ向け、Starと原文中のキー操作、共通3カラムと日次スクラップ・週候補、フォルダ操作と画像を順に実装する案とする。Shareの実装、通常Chatの自動添付調査、任意期間へのスクラップ、同期はこの改訂の必須範囲に含めない。

合成RSS／HTMLと一時DBで、重複スクラップ・保存失敗・Star付け外し・週境界・日付／タイムゾーン変更・保持期限後のノート・V1ストアの再open・画像の失敗を検証する。実機では原文の入力欄とIME、`j/k/s/n/Esc`、Notes往復、画像到着中の連続操作・選択・スクロール維持を確認する。初回ベータから残るVoiceOver・Reduce Motion・原文復帰位置などの受入は別途追跡し、仕様への記載を実機合格の証拠にしない。
