# Claude Desktop連携の技術検証（2026-10-04）

## 判定

**公式ディープリンクでの起動・依頼文の事前入力・添付・送信前停止と、ユーザーによる送信後の本文読取りを確認した。この環境での連携経路は技術検証PASSとする。Feeeder実装や異常系は未検証のため、PRD-05全体をPASSにはしない。**

`claude://cowork/new?q=…&file=…`を連携経路の候補として採用できる。今回の操作順は「Claudeを開く → Attachを許可 → 利用者が送信 → 親フォルダへのアクセスを許可 → 回答」だった。送信とは別に2回の許可操作が必要で、ファイルを探す操作は不要だった。ディープリンク由来の依頼文にはClaudeの赤い注意表示も出た。フォルダ許可が同じフォルダで毎回必要なのか、初回のみなのかは未検証。

## 再現経路と検証ツールの制約

[Claudeの公式案内](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link)のCoworkリンクを使った。生成済みURLをmacOSに直接渡すとClaudeへ到達した。通常チャット用の未文書化パラメータは試していない。

初回に作成した`.webloc`経由の起動は、ユーザーのTerminalで`_LSOpenURLsWithCompletionHandler()`の`-10400`エラーとなった。URLを直接`open`へ渡す方式で到達したため、製品実装では`.webloc`を介さずURLをOSへ渡す。

検証ツールから`file:`をブラウザで開く操作はブラウザのセキュリティポリシーで拒否された。エージェントによる迂回は行わず、各URLの起動とClaudeの通常終了はユーザーが実施した。エージェントはClaude UIの確認、合成ファイルのAttach許可、通常添付との比較、未送信の本文検証依頼文の準備と回答の照合を行った。

本文検証では、回答を入力欄に含めず、ファイルから5項目を答えるよう依頼した。得られた回答は`日本語`、`0500`・`END_A_20261004`、`https://source-b.example/article/2`・RSS要約のみ、`END_B_20261004`、`END_PACKAGE_20261004`で、元ファイルと一致した。Claudeの実行記録には、合成ファイルの親フォルダへのアクセス要求・許可と、そのファイルを`wc -c`・`cat`で読み取った出力が残っていた。ブラウザ検索や外部コネクタの利用は記録上確認されなかった。

## 実装・受入へ持ち越す事項

1. Feeederで確認済みパッケージを生成し、短い`q`と絶対パスの`file`をURLとしてOSへ渡す。Claude側のAttach、注意表示、送信後のフォルダ許可を利用手順で案内する。これらはClaude側のUIであり、確認を自動操作・回避することを製品の通常経路にしない。
2. 添付カードの存在だけで選択ソースが渡ったと判定しない。Feeeder実装後にも今回と同じ本文・出典の照合を行う。プレビューは失敗したが今回の本文読取りは成立したため、両者を区別する。469行目の表示の乱れは追加確認事項として残す。
3. 起動不能・添付拒否・不在ファイル・上限超過時のパッケージ保持と再試行を、Feeeder実装後に確認する。コピー／手動添付だけを通常経路の代わりにはしない。
4. 親フォルダへのアクセス要求が発生したため、選択したソースの生成パッケージだけを置いた専用の一時ディレクトリを渡す。ユーザーのライブラリや他のパッケージを同じディレクトリに置かない。一時ファイルは送信後にClaudeが読むため、起動成功を理由に直ちに削除しない。保持期限と削除タイミングは追加検証で決める。`/private/tmp`は使い捨ての作業領域であり、機密データの隔離境界ではない。

Spikeの合成ファイルとURLは一時ディレクトリに置き、本番コード・依存関係・DB migrationは変更していない。ビルド／既存テストは実行対象外。文書の整合性と`git diff --check`を確認した。
