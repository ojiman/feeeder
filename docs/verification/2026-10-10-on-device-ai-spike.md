# 端末内AI（FoundationModels・NaturalLanguage）のspike

更新日: 2026-10-10（日本時間）

テーマ中心のノート（[決定0008](../decisions/0008-theme-centered-notes.md)）と端末内AIの原則（[決定0009](../decisions/0009-on-device-ai-principles.md)）の判断材料として、使い捨てのスクリプトで2回の調査を行った。**製品コードは変更していない。スクリプトは調査後に削除したため再実行できない。** 方法と結果だけをここに残す。環境はApple Silicon / macOS 27.0.1 / Swift 6.4。入力は合成した日本語記事（タイトルとRSS要約）だけで、本人のライブラリ・購読・認証情報は使っていない。

## 1. 利用可否とテーマ分け

| 項目 | 結果 |
|---|---|
| `SystemLanguageModel.default.availability` | 利用可。日本語（`ja`）を含む24言語に対応。コンテキスト窓は4096トークン（入出力の合計） |
| 6テーマ×6件（36件）を一括でLLMにテーマ分けさせる | 16.6秒。6テーマ、36件すべて被覆、**純度0.57**。同じ分野を3つに割り、無関係な3分野を1つにまとめた。72件（4098トークン）と144件（6903トークン）は入力が上限を超えて失敗。1件あたり約57トークン |
| 1件ずつ既存テーマへ振り分けさせる（初回は命名、以後は番号選択） | 36件すべてが1テーマになった（22.6秒、1件平均0.63秒、失敗0）。プロンプトは1種類で調整していない。最初の試行は初回のテーマ0件の呼び出しで出力が暴走して失敗し、実装の誤りで結果が無効だったため、修正後の結果だけを採る |
| 日本語の文埋め込み・単語埋め込み（`NLEmbedding`） | どちらも利用不可（`nil`） |
| 日本語の文脈埋め込み（`NLContextualEmbedding`） | 資産が端末に存在し、512次元、最大系列長256。トークンベクトルの平均で記事ベクトルを作り、**全体の平均ベクトルを引いて中心化**し、平均連結の凝集クラスタリングで束ねた。中心化しないと全件が1塊になった（閾値0.30〜0.50） |
| 中心化後の閾値と結果 | 0.05: 5塊＋単独1、純度0.83（Swiftと LLMが混在）／**0.15: 6塊（6,5,7,6,5,6）＋単独1、純度0.97、36件で約3秒（埋め込み0.8秒を含む）、LLM不使用**／0.25: 7塊＋単独4、純度0.97。0.35は未取得 |

## 2. テーマ名の生成

| 方式 | 結果 |
|---|---|
| `@Generable`の`String`欄で名前を出させる | 3回×6クラスタ=18件中11件で、名前の後ろに「」}」と無関係な文章が続いた（名前の先頭部分は正しい）。3回とも出力上限60トークンを付けていたが、上限内で混入した |
| 指示文＋`maximumResponseTokens: 24`のプレーンテキスト | 2回×6クラスタ=12件すべて正常（「宇宙探査の進展」「Swift開発の課題」など）。1件平均0.51秒 |
| `@Guide(.pattern(...))`による正規表現制約 | 12件すべて失敗。10件が`UnsupportedGuide`、2件（睡眠の記事群）が「May contain sensitive content」 |

## 3. 問いの生成

4テーマ（各5記事）×5方式×2ラウンド=40回。1.3〜5.9秒。1回がガードレールの誤検知エラー（`Response may contain sensitive or unsafe content`、睡眠のテーマ、方式V3）。出力は筆者（Claude）が読んで評価したもので、PdMによる品質判断は別である。

| 方式 | 所見 |
|---|---|
| V0 素朴 | 記事の言い換えや事実確認が中心。3問と指示しても4〜5問出ることがある |
| V1 なぜ/どう違う/条件 | 指示した型の語句がそのまま出る。「どう違うのか、夜の習慣と朝の光の影響。」のように文として崩れたものがある |
| **V2 前提を疑う・反論** | 最も「考えさせる」問いが出た。例:「これらの習慣が効果的なのは誰に当てはまるのか」「小型モデルが、長い推論や事実の想起をサポートできるのはいつか」。文法の崩れたものも混ざる |
| V3 自分ごと化 | 指示文の文言（「自分の場合はどうか、…」）をそのまま貼り、中身が薄い。金融の記事では投資判断のような問いも出た |
| V4 論点→問いの2段 | 5〜6秒。途中の「論点」が箇条書きで乱れる。最終の問いに、記事をまたぐ良いものと一般的なものが混在 |

共通: 約3分の1が考えさせる問いで、残りは言い換えか文法の崩れ。出力形式が不安定（番号を付けない指示でも付ける、3行の指示で4〜5行）。モデルは記事に書かれたことしか知らない。V1・V3の出力が「定型の問い＋テーマ語」にほぼ等しかったことが、固定のレンズを用意する判断（決定0008）の根拠になった。

## 費用

Appleは、端末内モデルの推論は開発者にも利用者にも費用がかからず、アカウントやAPIキーも不要で、Apple Intelligence対応端末で有効にしていれば使えると説明している（[WWDC25 Meet the Foundation Models framework](https://developer.apple.com/videos/play/wwdc2025/286/)、[Apple Newsroom](https://www.apple.com/newsroom/2025/09/apples-foundation-models-framework-unlocks-new-intelligent-app-experiences/)）。これはAppleの説明であり、独立した検証ではない。WWDC26では端末内モデルが作り直され、Private Cloud Computeの利用も加わった（[WWDC26](https://developer.apple.com/videos/play/wwdc2026/241/)）。本アプリは後者を採用しない（決定0009）。この調査で使ったモデルの世代は確認していない。

## 未検証（PASSにしない）

- 合成データは分野がはっきり分かれた理想的な入力である。本人の実際のStarでのまとまり精度、日英混在、曖昧な記事は未確認。
- 数百件規模の速度（今回の素朴なクラスタリングは件数に対して計算量が増える）、メモリ、閾値の妥当性。
- 英語記事を日本語の文脈埋め込みへ入れたときの品質。
- Apple Intelligenceが無効な環境、資産が未取得の環境での挙動。
- 問いの質のPdM判断。レンズの具体化を実装したあとの出力の質。
- 試行回数が少ない（各方式1〜3回）。再現性は未確認で、モデルの出力は実行ごとに変わる。
- ガードレールの誤検知の頻度。
