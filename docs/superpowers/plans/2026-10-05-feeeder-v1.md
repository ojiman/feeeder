# Feeeder V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. AGENTS.mdに従い、同時writerは1名。Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 現在のRSS試作を、気持ちよく読み、週ノートを残し、確認した内容をClaude Desktopへ渡せるV1にする。

**Architecture:** SwiftUIの3カラムとSwiftDataを継続する。日時・記事同一性・ノート出典を期限付き本文から分離し、ネットワーク処理はMainActor外、保存と表示の更新はMainActorで行う。既存コードを段階的に拡張し、各段階で動くアプリと検証可能な差分を残す。

**Tech Stack:** Swift 6 / SwiftUI / SwiftData / Foundation URLSession・XMLParser / WebKit / CryptoKit。本文抽出にSwiftSoup 2.13.9を固定して追加する提案。

**Spec:** [PRD](../../specification.md)、[Architecture](../../architecture.md)、[Claude実機検証](../../verification/2026-10-04-claude-desktop-handoff.md)。実装者は本計画と3文書を読む。

## Global Constraints

- 「macOS 26.6以降を対象とするネイティブmacOSアプリ」。Backend、アカウント、同期、BYOK、他AI専用連携、アプリ内Language/Timezone設定は追加しない。
- 「Likeボタン・Like状態・Like期間は対象外」。モデル・UI・テストからLikeを取り除く。
- V1は専用保存先の空ライブラリから開始する。プロトタイプのデータ引き継ぎは利用者の2026-10-05の判断により対象外。
- 一覧のスクロールでは既読にせず、本文またはRSS要約の実表示を記録する。初回既読日時を再表示・再受信で更新しない。
- 読書UXは各UI Taskの受入条件。購読・記事の連続切替、慣性スクロール、原文からの復帰を、下記の利用者提供動画を参考に確認する。
- 月曜〜日曜の暦週、最大7暦日。初回ノート作成時に期間とTimezoneを固定する。夏時間のある週を固定168時間として計算しない。
- 「記事本文とRSS要約の保持期間は初期値30日」。ノートと採用済み出典タイトル・URLは自動削除しない。
- 「アプリは自動送信せず、返答をノートへ自動書込みしない」。起動成功をClaudeへの送信・読取成功として表示しない。
- 合成RSS/HTMLと一時DBだけで自動検証する。本人の読書DB、Keychain、ブラウザprofileを使わない。署名・配布・GitHub公開はこの計画の実行に含めない。
- 既存のworktreeを使い、各Taskをローカルcommitする。外部依存の追加時は固定版・ライセンス・解決差分を確認する。
- 改訂PRD全体と本計画は2026-10-05にPdMが実装開始を承認した。最終デモによる製品受入は別途、Task 9で明示的に承認を得る。

## Review Focus

1. 再起動でライブラリが初期化される：V1の購読・既読日時を保持し、通常起動でデモを挿入しない。Task 1 `readHistorySurvivesReopen`、`emptyLibraryRemainsEmptyAfterReopen`。
2. DST・Timezone変更で週がずれる：保存済み週の境界・候補・表示を変えない。Task 2 `frozenWeekSurvivesTimezoneChangeAndDST`。
3. レビュー後に本文が期限切れ／削除される：古いプレビューやAIコピーから本文が復活しない。Task 3 `expiredContentCannotBeReadOrReimported`、Task 7 `reviewInvalidatesWhenSourceExpires`。
4. 記事を高速切替中、前の記事の取得が遅れて返る：表示を取り違えず、取得だけでは既読にしない。Task 5 `lateExtractionDoesNotReplaceSelectedArticle`、Task 6の実機確認。
5. Claudeが不在ファイルにもAttachを表示する：存在・通常ファイル・読取・hash一致を起動前に検査する。Task 8 `invalidPackageNeverLaunchesClaude`。

**実装上の提案:** 記事の表示遷移は180msのease-out（fade＋移動方向に12pt）、原文の開閉は220msのease-in-outを開始値とする。購読／記事の選択highlightとスクロールはこのanimationに巻き込まない。連続入力では古い遷移を打ち切り最新selectionを表示する。Reduce Motionでは移動を省き、即時の表示切替にする。これらの時間・移動量は動画から測定した値ではなく、実機比較で調整する初期案。

**位置を保つルール:** 新しい記事の初回表示は先頭、戻った記事は本文の段落anchor＋段落内offsetへ復元する。原文・ノート・AIレビューからの復帰も同じ読書contextへ戻す。未読一覧では読んでいる選択行を保持し、次の記事への移動先は行の削除前の順序で決める。既読化や背景更新で選択行を突然消したり、一覧全体を先頭へ戻したりしない。取得本文が後から届いても、要約を読み進めている位置を自動でリセットしない。

**段階ごとの観察:** Task 1でクリック／j/kの即時反応、Task 2でノート編集と読書復帰、Task 4でrefresh中のスクロール、Task 5で遅延抽出と本文差替え、Task 7〜8でレビュー／取消からの復帰を確認する。不具合は発生したTaskで修正し、Task 6まで積み残さない。

**計測目標（提案）:** release build、合成10,000記事・100購読、保存済み本文で100回の選択切替と30秒の一覧／本文スクロールを3回ずつ実施する。入力イベント→表示更新開始のp95は100ms以下、当該操作中のアプリ起因の100ms以上のMainActor停止は0回を目標とする。遷移完了までの時間やネットワーク取得時間をこの数値に混ぜない。InstrumentsのSwiftUI／Hangs・Hitchesと操作区間のsignpostで、反復するコマ落ちの原因も調べる。計測方法は[AppleのSwiftUI性能分析](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance)と[応答性改善](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)を参照する。試験Mac、OS、display refresh rate、記事長、冷／温cacheを記録し、60/120Hzを一律の固定fpsにしない。数字の合格だけで読書UXを合格にせず、動画とReeder Classicを参考にPdMが操作感を確認する。

**Claude経路の位置づけ（2026-10-05追記）:** 通常Chatは、読書内容について相談する体験として利用者の第一希望。[公式案内](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link)では`claude://claude.ai/new?q=…`によるChatの起動・依頼文事前入力と、`claude://cowork/new?q=…&file=…`によるCoworkのファイル添付が記載されている。Chatの添付パラメータは記載されておらず、今回の実機検証でも未文書化パラメータは試していない。「Chatでは実現不可能」と結論づけたわけではない。Coworkの採用理由は、qの約14,000文字制約を受けずに本文をファイルで保持し、直接起動・添付の経路を確認できたこと。今回は経路調査を再開せず、確認済みのCoworkを実装案に保つ。Task 7のパッケージ生成とTask 8の起動処理は分離したままにし、将来Chatで同等の直接添付を確認できれば起動処理を差し替えられる構成とする。通常Chatへの手動添付をV1の通常経路に変えることや、未検証の自動添付を実装済みと扱うことは、この希望の記録に含めない。

## 共通の実行手順

各Taskの赤→緑を順に実行する。テスト前に未実装APIを使うテストがcompile失敗する場合も、その不足を赤の理由として記録する。

- 対象テストのコマンドは`swift test --scratch-path /private/tmp/feeeder-v1-build --filter <SuiteName>`。
- 各Taskのcommit前は全`swift test --scratch-path /private/tmp/feeeder-v1-build`と`git diff --check`。期待値は終了コード0、失敗テスト0件。
- UI変更時は`bash scripts/build-app.sh`。`--data-directory /private/tmp/feeeder-v1-demo-<task>`で作業用アプリを起動し、合成データで該当操作を確認する。
- Taskごとに既存テストの保持すべき契約を残す。Likeのテストは削除し、V1の既読記録・保存本文更新のテストへ置換する。
- 結果は対象commit／作業tree hash、fixture hash、環境、コマンド、終了コードと`PASS / FAIL / NOT_RUN / BLOCKED`を記録する。UIを自動テストだけでPASSとしない。

### Task 1: V1データモデルを整え、実表示の初回既読日時を記録する

**Interfaces:** `ReaderStore.init(url: URL, seedDemo: Bool = false, now: Date = .now) throws`。`markDisplayed(articleID: UUID, at: Date) throws`。`content(articleID: UUID, at: Date) throws -> ArticleContent?`。`ArticleContent: Sendable`は`articleID: UUID, text: String, summary: String, coverage: ContentCoverage, originalURL: URL?`。`ContentCoverage`は`feedProvided / extracted / summaryOnly / unavailable`。

- [x] **赤を書く:** `ReadHistoryTests`で一覧スクロール・選択のみでは`firstReadAt == nil`、実表示で`firstReadAt == displayedAt`、再表示／再受信／未読に戻しても初回日時不変を検査する。`readHistorySurvivesReopen`で同じV1の一時DBを再openし、購読・本文・既読日時の件数と値が一致することを検査する。`emptyLibraryRemainsEmptyAfterReopen`で空DBの通常起動／再起動にデモが勝手に増えず、`seedDemo`指定時だけ合成データが入ることをassertする。
- [x] **赤を確認:** `--filter ReadHistoryTests`でAPI不足または日時／初期化条件の不一致を確認する。
- [x] **保存を実装:** V1用の新しいschemaとして、Articleに初回取り込み時の必須`firstReceivedAt: Date`とoptional `firstReadAt: Date?`、ContentSnapshotに`coverageRaw`を持たせる。初回受信日時を再取り込みで変更しない。`SavedLike` entity・関連保存処理を削除し、`seedDemo`だけで合成デモを挿入する。
- [x] **初期保存先とエラーを扱う:** `RSSReaderApp.swift`の通常保存先を`Application Support/Feeeder/Reader.store`とする。`--data-directory`による合成検証は継続する。V1のDBを開けない場合は原因を表示して起動を止め、空DBへ自動resetしない。`failedOpenDoesNotResetStore`で開けない一時storeのbytesが書き換わらないことを検査する。
- [x] **表示とLike撤去を実装:** 非空の本文／要約が現在の記事ペインへ実表示されたcallbackからだけ`markDisplayed`を呼ぶ。Likeのscope・ボタン・shortcut・説明と本文更新を凍結する分岐を取り除く。保存失敗はrollbackして表示する。
